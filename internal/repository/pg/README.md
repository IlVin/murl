# Module: Postgres Repository Implementation

Реализация интерфейса `repository.RepoLinks` для работы с кластером PostgreSQL. Модуль оптимизирован для работы в распределенной среде с поддержкой шардирования.

---

## Особенности реализации

### 1. Атомарный UpSert
Вместо последовательных проверок `SELECT` и `INSERT`, используется единый SQL-запрос с Common Table Expressions (CTE). Это гарантирует:
*   Отсутствие состояний гонки (Race Conditions) на уровне БД.
*   Минимальное количество сетевых задержек (Round-trips).
*   Возврат корректного `ConflictFlag`.

### 2. Высокопроизводительный BatchUpSert
Метод пакетной вставки реализует сложную логику оркестрации:
1.  **Шардирование**: Входящие данные распределяются по бакетам шардов.
2.  **Конкурентность**: Для каждого задействованного шарда запускается отдельная горутина.
3.  **Batching**: Внутри горутин используется `pgx.Batch` для минимизации накладных расходов протокола Postgres.

---

## Использование

```go
cluster, _ := pgc.NewPgCluster(ctx, cfg, metrics)
repo := pg.NewPgRepoLinks(*cluster)

// Одиночная вставка
short, cf, err := repo.UpSert(ctx, "https://google.com")

// Пакетная вставка (выполняется параллельно по шардам)
result := repo.BatchUpSert(ctx, myBatch)
```

---

## Технические детали

### SQL запросы
*   **sqlUpSert**: Использует `ON CONFLICT (url) DO NOTHING` для безопасной параллельной вставки.
*   **sqlSet**: Реализует логику `Upsert` для принудительной установки соответствий (заменяет старый URL по существующему ID).

### Обработка контекста
В методе `BatchUpSert` предусмотрены частые проверки `ctx.Err()`. Если контекст отменяется во время выполнения, горутины прекращают работу, не дожидаясь завершения всех сетевых операций.

---

## Рекомендации

При использовании большого количества шардов (более 100) рекомендуется ограничить количество одновременно работающих горутин в `BatchUpSert` через **Worker Pool** или семафор, чтобы не превысить лимиты открытых файлов или дескрипторов.
