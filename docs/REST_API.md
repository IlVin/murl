# REST API

## API
Это программный интерфейс приложений, через который приложения взаимодействуют друг с другом.

## REST
Это программная архитектура, основанная на "**передаче ресурса и контекста в виде представлений их текущих состояний**" между клиентом и сервером, и, определяющая условия работы API.
REST не привязана к конкретным технологиям и протоколам

### Resource
Это адресуемая абстрактная информационная модель, отделяющая реальную архитектуру приложения от API.

### Контекст
Это совокупность метаданных и связей, описывающих условия существования и состояние ресурса и возможности взаимодействия с ним в текущий момент.

### Представление
Это реализация (сериализация) ресурса или контекста в конкретный, пригодный для передачи и обработки формат данных.

## RESTful API
Это REST API, привязанное к 
    + HTTP - протокол передачи данных
    + JSON, XML,... - формат представления


### Client
Это программа, которая получает доступ к ресурсам сервера.

### Server
Это программа, которая предоставляет доступ к ресурсам клиентам.

## Принципы REST
1. **Клиент-серверная архитектура** - Сервер предоставляет доступ к ресурсам, а клиент получает доступ к ресурсам
2. **Statelessness** - Независимость обработки запроса от контекста предыдущих взаимодействий. Сервер не хранит контекст клиента, а клиент не хранит контекст сервера. Клиент и сервер обязаны передавать свои контексты в объеме достаточном для обработки запроса/ответа.
3. **Cacheability** (кешируемость) - Каждое представление ресурсов для повышения производительности может быть помечено как кешируемоемое или не кешируемое
4. **Layered System** (Многоуровневая система) — клиент не должен знать, общается он напрямую с конечным сервером или с промежуточным узлом
5. **Uniform interface** (унификация интерфесов) - Все ресурсы должны быть доступны через единые правила
    + **Идентификация**: Каждый ресурс имеет уникальный адрес (URL)
    + **Стандартные методы**: Использование предсказуемых команд (в HTTP это GET, POST, PUT, DELETE)
    + **Самодостаточность**: Сообщение содержит всё, чтобы понять, как его обработать (например, указание формата JSON)
    + **Гипермедиа** — это принцип, при котором представление ресурса содержит ссылки на связанные ресурсы и возможные действия с ними, позволяя клиенту динамически перемещаться по API

# Вопросы

## Вопрос: «Где в REST хранится информация о том, что пользователь перешел на вторую страницу списка товаров?»
**Ответ**: Это Client State (Контекст). Он хранится на стороне клиента и передается в запросе (например, через URL-параметр ?page=2). Сервер не должен это запоминать.

## Вопрос: «Если мы используем токены в заголовках, нарушает ли это Statelessness?»
**Ответ**: Нет, так как токен — это самодостаточное представление контекста клиента. Сервер проверяет его «на лету» без привязки к сохраненной сессии.

## Вопрос: «Что будет, если сервер хранит JWT в базе данных и проверяет его при каждом запросе?»
**Ловушка**: Кажется, что это безопасно.

**Твой ответ**: Это нарушает принцип Statelessness. Если сервер лезет в базу, чтобы проверить статус конкретной «сессии» (токена), он начинает хранить Client State. В идеальном REST сервер проверяет подпись токена математически (в памяти), не обращаясь к хранилищу состояний.

## Вопрос: «Можно ли передавать команды в URL, например /users/delete/10?»
**Ловушка**: Это работает, так почему нет?

**Твой ответ**: Это нарушение принципа Uniform Interface. Согласно REST, URL должен идентифицировать Resource (существительное), а действие определяется Стандартным методом (глаголом HTTP). Правильно: метод DELETE по адресу /users/10.

## Вопрос: «В чем разница между PUT и POST?» (Классика)
**Твой ответ**:

    POST — это создание подчиненного ресурса (сервер сам решает, какой ID присвоить).
    PUT — это замена ресурса по конкретному адресу. Если ресурса нет, PUT его создаст по тому ID, который указал клиент.

**Важно**: **PUT** идемпотентен (10 одинаковых запросов дадут тот же результат, что и 1), а **POST** — нет (10 запросов создадут 10 записей).

## Вопрос: «Зачем нужен HATEOAS (Гипермедиа) на практике?»
**Твой ответ**: Чтобы сделать клиента независимым от изменений API. Если завтра адрес оплаты изменится с /pay на /checkout, сервер просто пришлет новую ссылку в JSON, и клиенту (фронтенду) не придется переписывать код и делать деплой — он просто нажмет на ту ссылку, которую прислал сервер.

## Вопрос: «Что самое сложное в REST?»
**Твой ответ**: Соблюдение всех ограничений сразу
